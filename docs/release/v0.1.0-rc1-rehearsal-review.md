### Phase C — fresh-install rehearsal findings (2026-10-28)

Fresh clone of `jeversole-consult/trainingbench` into
`~/tb-rehearsal/trainingbench/` on the dev host (same OS, same
NVIDIA driver, isolated project dir). Walked Steps 2 through 5 +
curl-based R9 verification. Steps 1 (system binaries) and smoke
training were skipped (same-host constraint).

- **🟡 F1 — INSTALL.md Step 5 shell-env gap.** The command
  `python -m uvicorn backend.api.main:app --host 0.0.0.0 --port $APP_PORT`
  requires `$APP_PORT` to be exported in the shell. The doc tells
  the operator to put `APP_PORT=8003` in `.env`, but doesn't tell
  them to export the vars from `.env` into the shell. A literal
  copy-paste from the doc would start the backend on port 8000
  (uvicorn default when `$APP_PORT` is unset in the shell), not
  the operator's configured port.
  - **Fix option A** (minimal): add a one-line note before the
    uvicorn command: `set -a; source .env; set +a` or equivalent.
  - **Fix option B** (cleaner): change the command to
    `python -m uvicorn backend.api.main:app --host 0.0.0.0 --port
    $(grep ^APP_PORT .env | cut -d= -f2 2>/dev/null || echo 8000)`
    — less elegant.
  - **Fix option C**: patch `main.py` to read `APP_PORT` from env
    at startup via uvicorn programmatic launcher. More refactoring
    than the current INSTALL.md flow deserves.
  - **Lean**: option A for v0.1.

- **🟡 F2 — INSTALL.md Step 5 behavior drift on password surfacing.**
  Step 5's "First-boot side effects" section claims the auto-
  generated admin password is *"printed to stdout + written to
  `logs/first-run-admin.txt`"*. In the Phase C rehearsal, **only
  the file was written** — no stdout banner surfaced the password.
  Operator who misses the file (hidden `logs/` dir, forgot to
  check) would be locked out.
  - **Fix option A** (doc): change the sentence to "written to
    `logs/first-run-admin.txt` (chmod 600). You'll see it on
    first login via the file." Remove the "printed to stdout"
    claim.
  - **Fix option B** (code): add a prominent stdout banner in
    the admin-password-bootstrap path (TB-US-049's seeder code).
    Operator attention is a feature.
  - **Lean**: option B — stdout banner matches operator mental
    model, prevents support friction. One `print(…)` call.

- **🟢 F3 — Rehearsal clean-numbering confirms TB-US-057
  "cosmetic AUTOINCREMENT drift" theory.** Live install has
  `training_set_version_id=3`, `rag_version_id=3`, `prompt_version_id=3`
  (noted in TB-US-057 Phase A notes as test-fixture residue).
  Fresh rehearsal install came up with `training_set_version_id=1`,
  `rag_version_id=1`, `prompt_version_id=2` — clean from fresh DB.
  Confirms the drift is not inherent to the seeder. No action
  needed; included here for documentation.

### Phase D — tag + release draft findings

- **🟡 F4 — Git metadata leaks operator email.** All 5 Phase B
  commits + the `v0.1.0-rc1` tag were created with
  `Jesse Eversole <eversolejesse@gmail.com>` via the global
  `git config user.email`. Phase A redacted the email from **file
  content** but did not touch git **metadata**. A public cut
  would expose the real email in every commit's Author / Committer
  field.
  - **Fix option A** (accept): common practice for personal OSS;
    operator's name + email become part of the commit record.
    No action.
  - **Fix option B** (project-local override + rewrite history):
    `git config user.email operator@example.com` + rewrite the
    arc of commits with `git filter-repo` or `git rebase -i` using
    the new identity. Destructive on a private repo; invisible
    to anyone following along.
  - **Fix option C** (reset the history): squash + rewrite to a
    single commit per logical group with the generic identity.
    Overkill for a solo project.
  - **Lean**: operator decides based on comfort. For a solo OSS
    project, option A (accept) is standard; the TB-US-005 story
    body should explicitly resolve this.

### TB-US-072 lab-machine acceptance findings (2026-10-28)

Captured during the lab-machine fresh-install sweep that TB-US-068
rolled forward. These findings expand on the host + WSL rehearsal
scope.

- **🟡 F2 — refined.** Credentials banner in stdout appears **after**
  the "Uvicorn running on http://..." line. Operators who treat
  the Uvicorn URL as the "install done" signal (reasonable
  expectation) miss the banner entirely. Lab-machine timing with
  a warm HF cache made the banner appear MUCH later than WSL;
  reinforces that `logs/first-run-admin.txt` is the reliable
  source, stdout is unreliable. **Lean fix**: ensure user
  creation + banner print happens BEFORE uvicorn's own startup
  completion line, OR update INSTALL.md Step 5 to tell operators
  the banner can come after "Uvicorn running".

- **🟡 F6 — Seeded experiments have `adapter_version_id=None`
  despite "plus-adapter" / "plus-rag" labels.** The seeder creates
  three draft experiments but can't pin an adapter_version_id
  (none exists until operator trains one). The label suggests
  functionality that isn't shipped. Operator who runs E2 via API
  gets a bare-base evaluation (same as E1). **Lean fix**: after
  TB-US-005, the first-run seeder re-runs on service restart +
  updates E2/E3 pins to whatever adapter is currently promoted;
  OR the labels get a `(pending adapter)` suffix when adapter_version_id
  is None.

- **🔴 ✅ F7a — Launch endpoint doesn't validate GSM8K dataset
  presence pre-spawn.** `POST /training/runs/launch` spawns
  `train.py` subprocess without checking the operator has run
  `scripts/download_gsm8k.py` first. Subprocess dies silently
  within 10s. INSTALL.md Step 6 tells operator to download first,
  so a literal follower is safe — but operator who skips that
  step (or uses the UI path once it ships) hits silent failure.
  **Status**: documented, not fixed in TB-US-074's scope.
  Candidate for a separate story if operator decides to tighten
  the ingress.

- **🟡 F7b — refined.** Subprocess errors DO land in `training_runs.notes`
  via reconciliation, but only when the `/training/runs` LIST
  endpoint is queried (not single-row GET). First-run operator
  querying `/training/runs/1` sees `status=running` even for
  dead subprocess until something triggers list-reconcile.
  **Lean fix**: make reconciliation fire on single-row fetch too.

- **🟢 F8 — No structured `error_message` column.** `training_runs`
  table has a `notes` column but no `error_message`. Errors land
  as free text in `notes`. Minor DX; doesn't block.

- **🔴 ✅ F9 — `train.py` logging_dir kwarg incompatibility
  with transformers 5.x.** Fixed as TB-US-074 (`f9366d5`).
  Smoke training now reaches the training loop.

- **🟢 F10 — API-shape clarity (not a bug).** Initial observation
  suggested `max_train_samples` was being dropped by TB-US-065's
  override block. Deeper investigation revealed the real issue:
  `LaunchTrainingRunRequest` Pydantic model requires hyperparameters
  under a nested `hyperparameters` dict field, not at top level.
  Unknown top-level fields are silently dropped by Pydantic's default
  behavior. With the correctly-shaped request (hyperparameters nested),
  all overrides apply correctly. Verified during TB-US-074 downstream
  verification: run_id=4 config column stored
  `{"max_train_samples": 50, "max_eval_samples": 25, "epochs": 1, ...}`
  and training honored all three (20s duration, matching 50 samples ×
  1 epoch).
  **Lean fix**: add `model_config = {"extra": "forbid"}` to
  `LaunchTrainingRunRequest` so Pydantic rejects unknown top-level
  fields with a 422. Would've caught my mistake with a clear error.
  Non-blocking.

- **🟢 F11 — Final loss columns not denormalized post-training.**
  `training_runs.final_train_loss` and `final_eval_loss` stay NULL
  after run completes, even when the `training_run_metrics` table has
  eval_loss entries. The data is captured; it just isn't propagated
  to the summary columns on the training_runs row. Minor DX issue —
  the UI (TB-US-066) + API consumers can get the final loss by
  querying the metrics table directly. Not blocking.
  Observed on run_id=4 (TB-US-074 verification run): step=4
  eval_loss=2.6373 in metrics table, but
  `training_runs.final_eval_loss` = NULL.
